# Next로 옮기면서 불리해진 점·단점 (트레이드오프)

Public 앱을 Vite SPA에서 Next로 옮기면서 생기는 단점이나 손해를 정리했습니다.  
이점은 `WHY-NEXT.md`에, 단점은 이 문서에 모았습니다.

---

| 관점 | 내용 |
|------|------|
| **배포 요구사항** | **Vite SPA**: 빌드 결과를 정적 파일만 올리면 됨 (Netlify Static, S3+CloudFront, GitHub Pages 등). **Next**: `/posts/[slug]` 같은 동적 라우트는 요청 시 서버에서 렌더하므로 **Node 서버**가 필요함. Vercel/Netlify(SSR 지원)/Railway 등으로 배포해야 하고, 완전 정적 호스팅만 쓰려면 `output: 'export'`로 정적 내보내기를 해야 하는데, 그러면 동적 라우트는 빌드 시점에 알 수 있는 slug만 가능해짐. |
| **빌드·개발 속도** | **Vite**는 dev 서버·HMR이 매우 빠른 편. **Next**는 빌드와 dev가 상대적으로 무겁고, Cold start가 있을 수 있음. 로컬에서 저장하면 바로 반영되는 체감은 Vite가 나을 수 있음. |
| **복잡도·개념** | Server Component / Client Component 구분, `'use client'`, 서버에서는 `window`/`localStorage` 사용 불가, API base를 서버/클라이언트에서 다르게 써야 함 등 다루어야 할 개념이 늘어남. 팀에 Next 미경험자가 있으면 학습 비용이 있음. |
| **환경 변수** | `NEXT_PUBLIC_*` 만 클라이언트에 노출됨. 실수로 API 키나 비공개 값을 `NEXT_PUBLIC_` 에 넣으면 노출 위험이 있음. 서버 전용과 클라이언트용 변수를 구분해서 관리해야 함. |
| **디버깅** | 에러가 서버 렌더 단계에서 나는지 클라이언트(브라우저)에서 나는지 구분해야 할 때가 있음. 스택 트레이스와 로그 위치가 SPA만 쓸 때보다 한 단계 더 신경 쓸 부분이 생김. |
| **캐싱·최신성** | Server Component에서 매 요청마다 API를 호출하면 항상 최신이지만, Next/플랫폼 쪽 캐시를 쓰면 글이 갱신돼도 잠시 오래된 데이터가 보일 수 있음. `revalidate` 등 캐시 전략을 의도대로 설정해야 함. |

---

**요약**: 배포는 정적 파일만 올리면 끝이 아니라 동적 라우트를 쓰는 한 Node(또는 호환 런타임)가 필요해지고, 개발 경험·복잡도는 올라가며, 빌드/개발 속도는 Vite보다 무거울 수 있음. 대신 SEO·첫 화면·공유 미리보기 쪽 이득을 위해 Next로 옮긴 상태임.
